# 评审修复 Team 方案

## 1. 目标

为当前项目设计一套专门处理**评审、问题修复、回归验证**的 team。

这套 team 的职责不是做新功能，而是确保现有功能：

- 更稳定
- 更一致
- 更少回归
- 更容易上线

## 2. 适用场景

这套 team 适合处理以下任务：

- 代码 review
- PR 评审意见修复
- Bug 修复
- UI 细节修正
- API 逻辑修复
- 数据结构兼容修复
- 回归验证

## 3. 设计原则

### 3.1 先评审，再修复，再验证

所有问题都按固定顺序处理：

1. 发现问题
2. 分类问题
3. 定位修复
4. 验证结果

### 3.2 评审与修复职责分离

避免一个角色同时负责发现问题和修复问题，否则容易漏掉边界。

### 3.3 轻量闭环

不做复杂的审计系统，不做大规模流程编排。

目标是让修复动作快速闭环。

### 3.4 以稳定性优先

修复时优先考虑：

- 不破坏现有功能
- 不引入新复杂度
- 尽量最小改动

## 4. 推荐团队编制

建议采用 **3 个角色**，已经足够覆盖评审和修复工作。

### 4.1 Agent A: 评审 Agent

**职责**

- 阅读需求或 PR
- 找出问题
- 判断严重程度
- 标记风险点
- 明确哪些必须改，哪些可优化

**擅长的事**

- 逻辑漏洞识别
- UX 风险识别
- 接口契约检查
- 数据一致性检查
- 命名和结构审查

**输出内容**

- 问题清单
- 严重级别
- 影响范围
- 修复建议

### 4.2 Agent B: 修复 Agent

**职责**

- 根据评审结论修改代码
- 实现最小修复
- 保持风格一致
- 避免扩散改动范围

**擅长的事**

- 修复 bug
- 调整组件
- 修改 API
- 修正 schema
- 补齐边界条件

**输出内容**

- 修复说明
- 修改文件列表
- 关键变更点
- 剩余风险

### 4.3 Agent C: 验证 Agent

**职责**

- 复查修复结果
- 检查是否真的解决问题
- 判断有没有引入回归
- 输出是否可合并 / 可上线

**擅长的事**

- 回归检查
- 边界测试
- 路由检查
- 数据流程检查

**输出内容**

- 验证结论
- 是否通过
- 仍存在的问题
- 下一步建议

## 5. 推荐工作流

### 5.1 标准流程

1. 评审 Agent 先读需求、截图或代码变更
2. 评审 Agent 输出问题清单
3. 修复 Agent 按优先级修复
4. 验证 Agent 复查修复结果
5. 如有残留问题，回到第 2 步继续迭代

### 5.2 适合并行的部分

- 多个独立问题可拆开修
- 前端样式和后端逻辑可以分别修
- 文案问题和状态问题可以并行检查

### 5.3 必须串行的部分

- 先评审，再修复
- 先修复，再验证
- 验证未通过不能进入下一轮

## 6. 针对当前项目的评审重点

这个项目是匿名协作式每日功课系统，所以评审时重点检查这些方面：

- 今日页是否足够轻
- 团体页是否突出“共同完成”
- 我的页是否保持克制
- 管理员模块是否不会污染前台
- 数据库变更是否兼容现有打卡逻辑
- 后台改动是否破坏匿名感

## 7. 评审分类建议

建议把问题分成 4 类：

### 7.1 P0

严重问题，必须立即修复。

例子：

- 登录失效
- 打卡写入失败
- 数据丢失
- 权限绕过

### 7.2 P1

高优先级问题，影响核心体验。

例子：

- 团体完成状态错误
- 页面核心按钮不可用
- 管理员无法进入后台

### 7.3 P2

中等问题，可在同一轮修复。

例子：

- 文案不一致
- 页面间状态不统一
- 视觉层级略乱

### 7.4 P3

低优先级优化项，可延后。

例子：

- 边距微调
- 动效优化
- 次要布局调整

## 8. 修复原则

### 8.1 最小改动

优先只改必要文件，不扩散到无关模块。

### 8.2 保持一致性

修复时必须和现有架构、命名、组件风格一致。

### 8.3 不顺手重构

不要借着修 bug 的机会大范围重构。

### 8.4 修复必须可验证

每次修复都要能明确回答：

- 改了什么
- 解决了什么
- 怎么验证

## 9. 推荐的产出格式

### 9.1 评审 Agent 输出格式

- 问题列表
- 严重级别
- 影响文件
- 修复建议

### 9.2 修复 Agent 输出格式

- 修复目标
- 修改文件
- 具体改动
- 未覆盖风险

### 9.3 验证 Agent 输出格式

- 验证方法
- 验证结果
- 是否通过
- 是否需要二轮修复

## 10. 最小可用版本

如果你想先跑一个最轻量版本，建议只保留：

1. 评审 Agent
2. 修复 Agent
3. 验证 Agent

这已经足够覆盖绝大多数修复流程。

## 11. 不建议的扩展

当前项目不建议立即加入：

- 专门的性能分析 Agent
- 专门的安全审计 Agent
- 专门的测试生成 Agent
- 专门的文档整理 Agent

这些角色在当前阶段收益不大，反而会增加协作成本。

## 12. 结论

这个“评审修复 team”最适合采用三段式闭环：

1. 评审发现问题
2. 修复最小改动
3. 验证是否真正解决

它适合当前项目的原因是：

- 简单
- 直接
- 可重复
- 不干扰主开发节奏

如果后续项目变大，再考虑把评审、修复、验证继续细分。
