# 管理员模块 Plan

## 1. 模块目标

管理员模块的目标不是做一个复杂后台，而是给当前匿名每日功课系统提供一套**最小可用的运营控制台**，用于管理系统事项、团体、成员和每日运行状态。

管理员模块要解决的核心问题：

1. 系统事项谁来维护
2. 团体如何被创建和管理
3. 用户和成员出现异常时如何处理
4. 每日打卡和结算如何查看
5. 后续如何支持运营配置，但不破坏产品克制感

## 2. 当前约束

结合 `AGENTS.md`，管理员模块需要遵守以下技术和架构约束：

- 项目是单体全栈应用，不做 monorepo
- 技术栈固定为 `Next.js 15 + React 19 + TypeScript`
- 数据库使用 `SQLite`
- 鉴权使用 `jose`
- 密码加密使用 `bcryptjs`
- 日期统一使用 `date-fns` 相关的日期工具
- 全站文案使用中文
- 页面和 API 都在同一个项目内实现

## 3. 管理员模块定位

管理员模块不是给普通用户看的页面，而是给运营或开发者使用的内部后台。

### 3.1 管理员能做的事

- 查看全局概览
- 管理系统预设事项
- 查看团体列表
- 查看团体成员
- 查看某天的打卡完成情况
- 处理异常用户或异常团体
- 维护邀请码或团体基础信息

### 3.2 管理员不做的事

- 不做社交聊天
- 不做复杂统计报表
- 不做排行榜
- 不做公开社区
- 不做多角色复杂权限体系

## 4. 角色与权限

### 4.1 角色建议

建议在现有 `User` 基础上增加一个管理员标记，优先保持简单：

- `isAdmin: boolean`

如果后续需要扩展，再升级为：

- `role: "user" | "admin" | "superadmin"`

### 4.2 权限边界

- 普通用户只能访问自己的业务页面
- 管理员只能访问 `/admin` 下的页面和管理接口
- 所有管理接口都必须做服务端鉴权

### 4.3 鉴权方式

继续沿用现有 JWT Cookie 方案：

- 登录后从 session 中识别管理员身份
- 服务端组件和 API 都需要统一做权限校验

## 5. 推荐的后台路由

建议新增独立后台路由段：

```text
app/admin/
  layout.tsx
  page.tsx
  tasks/
  groups/
  users/
  checkins/
  settings/
```

### 5.1 路由职责

- `app/admin/page.tsx`
  - 后台首页总览
- `app/admin/tasks/`
  - 系统事项管理
- `app/admin/groups/`
  - 团体管理
- `app/admin/users/`
  - 用户与成员管理
- `app/admin/checkins/`
  - 打卡与结算查看
- `app/admin/settings/`
  - 系统设置与基础配置

## 6. 核心页面规划

### 6.1 后台首页

展示当前系统的整体运行状态。

建议内容：

- 今日活跃团体数
- 今日完成中的团体数
- 今日全员完成团体数
- 待处理异常数量
- 系统事项启用数量

### 6.2 系统事项管理

这是后台最核心的页面之一，因为当前产品的事项是“系统下发”的。

建议支持：

- 查看事项列表
- 启用 / 停用事项
- 调整排序
- 编辑事项标题
- 区分团体事项和个人事项

建议不做：

- 用户自定义新增事项

### 6.3 团体管理

用于查看和处理团体信息。

建议支持：

- 查看团体列表
- 查看团体名称、邀请码、创建时间、成员数
- 进入团体详情
- 手动禁用团体
- 重置团体基础状态

### 6.4 用户与成员管理

用于处理用户异常和成员关系。

建议支持：

- 查看用户列表
- 查看用户手机号、创建时间、所属团体
- 查看团内昵称
- 处理异常成员关系
- 必要时支持封禁或移除成员

### 6.5 打卡与结算查看

管理员需要能快速看到某一天的整体情况。

建议支持：

- 按日期查看团体完成状态
- 查看某个团体的事项完成明细
- 查看某个成员的打卡记录
- 查看某天是否全员成功

### 6.6 系统设置

用于少量全局配置。

建议内容：

- 系统事项是否开启
- 默认团体事项配置
- 默认个人事项配置
- 邀请码生成策略

## 7. 数据模型规划

当前 schema 已有：

- `User`
- `Group`
- `GroupMember`
- `Task`
- `Checkin`

管理员模块建议只做最小增量，不要重构太大。

### 7.1 推荐新增字段

在 `User` 上增加：

```ts
isAdmin Boolean @default(false)
```

### 7.2 可选新增表

如果后续需要记录后台操作，再增加：

- `AdminLog`

示例字段：

```ts
{
  id,
  adminId,
  action,
  targetType,
  targetId,
  payload,
  createdAt
}
```

但这一步可以放到 V1.1，不必一开始就加。

## 8. 管理接口规划

建议后台接口与普通用户接口分开，避免混乱。

### 8.1 路由建议

```text
app/api/admin/tasks/*
app/api/admin/groups/*
app/api/admin/users/*
app/api/admin/checkins/*
app/api/admin/settings/*
```

### 8.2 接口原则

- 所有接口必须校验管理员身份
- 所有修改类接口必须记录操作者
- 查询接口尽量支持分页
- 删除操作优先做软禁用，不直接物理删除

## 9. 信息架构建议

后台左侧导航建议保持简单：

- 总览
- 事项
- 团体
- 用户
- 打卡
- 设置

不要扩展成复杂 CRM 式后台。

## 10. MVP 级后台范围

### 10.1 第一阶段必须做

- 管理员登录识别
- 后台首页
- 系统事项管理
- 团体列表查看
- 用户列表查看
- 打卡记录查看

### 10.2 第二阶段再做

- 团体禁用
- 用户封禁
- 日志记录
- 配置化系统事项
- 日期维度结算页

### 10.3 暂不做

- 多角色权限系统
- 复杂审批流
- 操作审计中心
- 图表大屏
- 导出 Excel

## 11. 开发顺序建议

建议按下面顺序推进管理员模块：

1. 管理员身份识别
2. `/admin` 路由骨架
3. 后台首页总览
4. 事项管理
5. 团体管理
6. 用户管理
7. 打卡查看
8. 系统设置

这个顺序的好处是先把“能看、能管、能查”打通，再考虑更细的运营能力。

## 12. 与现有产品的关系

管理员模块的存在目的，是为了支撑当前已经完成的 V1 产品，而不是改变产品方向。

它应该服务于以下事实：

- 前台保持极简
- 后台承担运营复杂度
- 前台用户看不到后台噪音
- 产品气质不被破坏

## 13. 成功标准

管理员模块做完后，应该满足：

1. 运营人员可以快速查看全局运行状态
2. 系统事项可以被稳定维护
3. 出现异常时可以定位到团体、用户和打卡记录
4. 不需要改前台产品气质，就能支持后续运营

## 14. 结论

管理员模块应该是一个**轻量、克制、可维护**的内部后台。

最佳路线是：

- 基于现有 Next.js 单体项目继续扩展
- 复用现有鉴权和数据库
- 先做最小后台闭环
- 不引入过重权限和报表系统

这能保证后台“够用”，但不会反过来拖慢前台产品。
